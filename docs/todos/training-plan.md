# 训练计划模块待办

这份清单记录 Heal View 训练计划模块的产品约定、第一阶段实现范围和后续扩展方向。模块继续保持单用户、本地优先的定位，不提供医疗诊断或教练服务。

## 产品模型

- **训练计划**：一个长期目标，例如“2026 年减肥计划二期”，包含整体目标、起止日期，以及「生命周期」和「达成度」两个维度（见下文）。
- **训练阶段**：计划中训练方案发生变化的阶段，例如 7-8 月基础训练、9 月恢复训练、10-12 月强化训练。阶段需要支持暂停、顺延、提前结束和调整原因；它不直接承载训练单元。
- **训练单元**：某个具体日期应完成的一整套训练安排，直接关联所属训练计划。
- **训练项目**：训练单元中的单个项目，例如健走、椭圆机、平板支撑或高拉背器（正手）。同一个器械的不同握法或方向算不同项目，器械名放在 `equipment` 字段里。
- **阶段反馈**：训练阶段结束后填写一次，不要求每日手动反馈。

当前计划中的“反馈周期”是阶段结束，而不是固定按月。阶段日期可以跨月，也可以因为手术、身体状态或其他原因顺延。

## 计划的两个维度

计划不只有一个状态。它有两个**正交**的维度，刻意分开、不能合并成同一个字段：一个回答“现在处在什么时间位置”，一个回答“该练的日子我履约了多少”。

### 1. 生命周期：由日期推导，不落库

| 取值 | 含义 |
| --- | --- |
| `draft` | 今天早于开始日期 |
| `active` | 今天落在起止日期之间 |
| `ended` | 今天晚于结束日期 |

- **不存字段**：一旦把“进行中”存下来，就会和阶段状态、训练单元状态形成多个真相来源。
- 唯一推不出来的意图是“我不想再看到它了”，所以只存 `archived_at` 一个可空时间戳。
- **归档与生命周期正交**：可以归档一个进行中的计划（即放弃），它仍然是 `active`，只是默认不再出现。
- **计划开始后只能延长，不能提前结束**：计划已开始时不允许把 `end_date` 改小。要提前结束，用阶段级手段——计划详情里的「取消该阶段」，或删除该阶段未来的训练单元；要整体放弃，用归档。取消阶段会让它覆盖的训练日退出达成度，所以手术或身体状态导致的提前结束不会倒扣分。

### 2. 达成度：由训练单元和导入记录推导，不落库

打卡口径：**计划一旦开始就不能停止**，该练的那天没有打卡就是缺席。

- **分母**：已过期、且不被任何 `cancelled` 阶段覆盖的训练日（按日期去重）。
- **分子**：履约日 + 加练日。
  - **履约日**：该日任一训练单元的派生状态是 `achieved` 或 `partial`。部分达标算履约——人来了、卡打了；做多做少交给训练质量指标（`verifiableCompletionRate`）去评价。
  - **加练日**：计划区间内、当天没有训练单元、但有匹配该计划任一动作 `sport_types` 的导入记录的日子。加练计入分子，所以**比率可以超过 100%**，表示以量补欠。
- **没有导入数据同样算缺席**，不单独成档。判断“是没练还是没同步”不是统计的职责，而是补卡入口的职责。
- **被取消的阶段完全退出达成度**：既不算分母，也不算分子。这样因为手术或身体状态终止的阶段不会倒扣分。
- 分子分母都是“天”，但加练可以让分子超过分母，所以**不要给比率设 100% 上限**。
- 分母为 0 时不给比率也不给档位（显示“暂无”），不要误报成“完全缺席”。

档位取半开区间，边界不重叠：

| 档位 | 区间 | 文案 |
| --- | --- | --- |
| `complete` | `[100%, ∞)` | 全部完成 |
| `minor_gaps` | `[75%, 100%)` | 偶有空缺 |
| `slight_shortfall` | `[50%, 75%)` | 略有缺口 |
| `clear_shortfall` | `[30%, 50%)` | 缺口明显 |
| `barely_trained` | `(0%, 30%)` | 基本没练 |
| `absent` | `{0%}` | 完全缺席 |

展示约定：

- **进行中只显示比率，不显示档位**：刚开跑 5% 的计划不该被下判决。
- 档位旁边必须能看到**数据覆盖率**，让低分可解释——是没练，还是导入链路断了。
- 保留一位小数并同时给出分数（`18/24 · 75.0%`），避免四舍五入后档位看起来自相矛盾。

### 补卡

“无数据 = 缺席”成立的前提是漏打卡可以补救，所以补卡入口是这个口径的地基，不是可选装饰：

- 计划详情里，已过期且没有履约的训练日要有明确的补卡入口。
- 手机端切到过去日期时，要提示“这天还没打卡，可以现在补”。

## 推荐数据结构

第一阶段建议使用以下业务表：

```text
training_plans
training_phases
training_sessions
training_session_items
training_phase_reviews
```

- `training_plans`：保存整体计划和目标。
- `training_phases`：保存训练方案发生变化的阶段；周期不是简单的计划字段，因为不同阶段可能有不同训练内容。
- `training_sessions`：保存具体日期的训练单元，直接关联训练计划，避免未来修改计划时改变历史安排。
- `training_session_items`：保存训练单元中的单个有氧或力量项目及其目标。
- `training_phase_reviews`：每个训练阶段最多一条正式反馈，记录阶段总结、疲劳、不适、体重变化和调整意见。

阶段结束反馈不要求绑定某一天，也不创建每日反馈表。

### 状态口径

| 状态 | 含义 |
| --- | --- |
| 达标 | 匹配到导入记录，且所有可核对目标都达到 |
| 部分达标 | 匹配到导入记录，但至少一项可核对目标未达到 |
| 无数据 | 训练日已过，但没有匹配到任何导入记录 |
| 无法验证 | 项目没配置导入类型、没有可核对目标，或记录缺少可核对字段 |
| 待开始 | 训练日还没到，暂时没有可匹配的数据 |
| 未完成 | 只用于人工项目：计划日已过且没有任何人工确认记录 |

### 「提前结束」为什么必须是显式动作

“计划开始后只能延长”需要一个逃生口，否则因为手术或身体状态中断的用户只能被倒扣分。
达成度分母排除被 `cancelled` 阶段覆盖的日子，所以**取消阶段就是那个逃生口**。

但这里有个陷阱：`training_sessions` 只挂 `plan_id`，阶段归属是读取时按日期区间推断的，
而缩短阶段 `end_date` **不会**裁剪既有的训练单元。所以只改日期会留下一批不属于任何阶段的
“孤儿”训练日，它们仍留在分母里——等于没生效。因此界面上提供的是显式的「取消该阶段」，
而不是让用户去改日期。

反过来说，**不**把“不属于任何阶段”当作退出分母的依据：计划可以合法地没有阶段
（`POST /training-plans/with-sessions` 就允许），那样会让分母直接归零。

### 一个刻意保留的不一致

全局训练单元浏览页（`/plans/sessions`）仍会列出已归档计划的训练单元。归档目前只从
计划列表和手机端今日训练隐藏；那个页面是用户主动查历史的地方，暂时不做过滤。

### 迁移为什么用 DROP COLUMN 而不是重建表

`training_phases` 和 `training_sessions` 都以 `ON DELETE CASCADE` 指向 `training_plans`，而生产在
`server/src/services/database.js` 里显式开启了外键。**重建计划表会连带删掉全部阶段和训练单元。**
`ALTER TABLE ... DROP COLUMN` 走的是内部改写，实测（外键开启）不会触发级联，子表数据完好。

原来的迁移测试用的是裸连接（外键默认关闭），会掩盖这类问题，所以补了一个在外键开启前提下
跑 v10 并断言子表数据存活的用例。以后动这几张表的结构前先看它。

### 为什么"删除筛选结果"由服务端重新求交

跨页全选如果做成"客户端把所有 id 取回来再回传"，就得先把上千个 id 塞进请求体，而且从取回列表到提交
删除之间数据随时可能变，两边对不上时用户看到的条数和实际删掉的条数会不一致。改成把**同一份条件**交给
服务端，由它用列表用的那条查询路径重新求交，`total`、确认弹窗里的条数和真正被删的行必然是同一批。

### 为什么关键词只搜训练内容

圈定"加错的那一批"时，真正能区分的线索是**训练项目**（批量规则配错了项目），而单元名称和备注是自由
文本：备注里写着"手术后减量"的单元本来就要留着，却会因为搜到"减量"两个字混进删除范围。所以这个条件
只匹配项目名，名称和备注一律不参与，搜它们必然是 0 条。工具栏里它也从最右边挪到了最左边，因为它是
几个条件里最常用的入口。

### 打卡状态为什么能直接在 SQL 里筛

"有没有打卡"就是 `training_session_logs` 里有没有对应那一行（`session_id` 是 UNIQUE），所以它是**存量
事实**，可以用 `EXISTS` / `NOT EXISTS` 直接筛，不需要像完成状态那样读取时推导——后者要算有氧匹配、
过期换算和人工优先，SQL 里根本表达不出来。两者刻意不合并：

- 有氧项目可以靠导入记录算成达标，但那天并没有打卡记录（列表里就是"达标 + 未打卡"）。
- 反过来补一次卡会把完成状态从"未完成"改写成"全部完成"，但打卡状态在补卡前后就是翻转的那一位。

列表里"已打卡"标签放在日期旁边而不是完成状态旁边，也是因为这两个维度不该被读成一个：日期那一列回答
"这天到底确认过没有"，完成状态那一列回答"练得怎么样"。

### 为什么条件删除必须带 expectedCount

确认弹窗里那个"将删除 N 个训练单元"是**用户点头的对象**。服务端按同一份条件重新求交之后，如果命中的
不是 N 条，说明从渲染数字到提交之间条件或数据已经变了（另一个页面删过、计划刚被改过），这时候执行等于
删掉用户没确认过的那一批。所以 `{ filter }` 必须同时给 `expectedCount`：对不上返回 409
`SESSION_DELETE_COUNT_CHANGED`（附 `details.matchedCount`），客户端收到后关掉弹窗、清空勾选、重新拉列表，
让用户看着新的条数再决定；不带这个字段直接 400，不接受"条件合法就顺手删一批"的调用方式。

这条约束也是对自己人下手：脚本或调试请求如果只丢一个条件过去，拿不到"删掉了什么"的确认，只会得到 400，
不会再出现"本想验证拒绝逻辑、结果把真实数据删了"这种事。按 id 删除不需要它——id 列表本身就是完整的声明。

### 为什么删除对筛选条件比列表更严

列表对认不出的条件一直是宽容的（传 `status=planned` 就当没筛），因为最坏结果只是多显示几行。
删除不行：`status=planned` 被静默忽略后，用户以为自己在删"待开始的那批"，实际删掉的是整个计划——
这类入口宁可 400 也不能猜。同理，一个条件都不给的 `{ filter: {} }` 等于"删掉全部训练单元"，
这个入口不存在这种用法，直接拒绝（`SESSION_DELETE_FILTER_REQUIRED`）。

### 为什么绝不把训练单元删空

某个单元只剩这一个项目时跳过它并把跳过数回报给界面，而不是顺手把单元也删掉：

- 空单元没有任何目标可打卡，也会被既有的"单元至少要有一个训练项目"校验挡在编辑弹窗外面，属于半死状态；
- "删内容"和"删单元"是两种意图，前者不该悄悄升级成后者。真想清掉这种单元，用训练单元的批量删除。

删掉中间的项目不会重排剩下的 `position`（留空洞不影响顺序和追加逻辑），这是有意的：重排要重写整张表，
而空洞没有任何可观察到的副作用。
